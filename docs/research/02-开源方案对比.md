# 开源与现成方案对比

核验日期：2026-10-06 UTC。依据官方文档、仓库默认分支许可证与公开维护数据。本文区分“具备服务端注入模式”和“已通过隔离验收”：前者可从文档核验，后者必须在具体权限配置下实测；本次未部署、未做渗透测试。

## 先给选型结论

1. **优先验证 Infisical Agent Vault + FastMCP。** 前者已经有独立配置 UI、凭据存储和转发注入，后者负责少量业务工具及 OpenAPI 起步。先用合成假密钥验证，不搭完整 Infisical 平台。
2. **OAuth 接入数量上来后再考虑 Nango。** 它提供实际鉴权代理及刷新基础设施，但当前许可证是 ELv2，不能当作 MIT 组件随意包装成托管平台。
3. **只想快速接国外现成应用可考察 Composio/Pipedream。** 二者确实有服务端凭据托管/执行模式，但公开 SDK 或组件仓库不等于完整托管后端可自由自部署；国内供应商覆盖仍需核验。
4. **模型统一与自动切换需要时再加 LiteLLM/New API/Bifrost。** 不作为凭据安全边界的默认总底座。当前 LiteLLM 和 Bifrost 已有 MCP 网关能力，称它们“仅有模型路由”不准确。
5. **ContextForge 留作多 MCP 服务管理的备选。** 单用户、少量工具不必先上完整网关。

这些是本项目判断，并非厂商安全背书。

## 能力对照

“隔离判断”均假定 AI 没有代理主机、管理员身份或密钥存储访问权。

| 方案 | 官方确认的主要能力 | 是否属于上游凭据代理 | 对本项目的适用性 / 缺口 |
| --- | --- | --- | --- |
| [Infisical Agent Vault](https://github.com/Infisical/agent-vault) | 单一二进制、管理 UI、SQLite、HTTP(S) 代理；服务规则匹配目标并注入鉴权 | **是，直接针对 AI 的 broker**；官方要求与 AI 分开部署 | 首选试验。MIT 核心；目前 Preview；HTTPS MITM 有 CA/网络配置成本；SSH、任意 OAuth 与云签名仍需另外处理 |
| [FastMCP](https://github.com/PrefectHQ/fastmcp) | Python MCP 框架、工具 schema、OpenAPI 生成 | **框架能在服务内注入，自己不是凭据管理产品** | 薄工具层首选；默认导入全部端点，需要明确 allowlist；身份隔离由部署决定 |
| [Nango](https://github.com/NangoHQ/nango) | 用户连接、API Key/OAuth/刷新、Proxy、Functions、MCP | **是，Proxy 注入上游鉴权** | OAuth 复用价值高。注意 Proxy 的 `Base-Url-Override` 和原样响应，不能直接给模型无约束访问 |
| [Composio](https://github.com/ComposioHQ/composio) | 托管连接、工具执行、Proxy Execute、MCP | **是，托管模式服务端注入，连接查询默认遮蔽凭据** | 可快速验证常见应用。公开仓库主要是 SDK/生态接入；自托管/VPC 是企业安排，非 MIT SDK 自动附带的后端 |
| [Pipedream Connect](https://pipedream.com/docs/connect/api-proxy) | 连接授权、预制动作、API Proxy、MCP | **是，Proxy 自动注入连接鉴权** | 有 allowed domains；官方 Proxy 当前单请求最多 30 秒，长视频任务应分提交/查询；仓库不是完整 SaaS 服务的自由替代 |
| [LiteLLM](https://github.com/BerriAI/litellm) | 模型统一、虚拟 Key、路由；当前也有 MCP 网关、上游凭据及 OAuth 管理 | **在代理正确配置时可藏上游 Key；不是仅路由** | 模型兼容与 MCP 管理可复用。不能给 AI master/admin Key；SSH、通用厂商协议不是自动覆盖 |
| [New API](https://github.com/QuantumNous/new-api) | 多模型/多模态 API 统一、渠道凭据、令牌与用量管理 | **模型渠道代理能注入 Key，范围主要是模型 API** | 中文模型渠道选择可参考；不是任意业务 API/OAuth/SSH 操作中心；AGPL-3.0 |
| [One API](https://github.com/songquanpeng/one-api) | OpenAI 格式模型聚合、渠道与令牌 | **模型渠道代理** | 原项目相对旧；优先参考活跃的 New API 或其他网关，不作为新项目首选 |
| [Bifrost](https://github.com/maximhq/bifrost) | 模型路由、多模态、Web 配置；当前文档还有 MCP client/gateway、工具过滤、OAuth | **服务内凭据模式可用；不能仅贴“模型路由”标签** | Go 方案备选。README 将 MCP gateway 等列入企业能力，文档又存在相关基础能力；免费版本边界要对固定 OSS 版本实测，不能承诺全部可用 |
| [IBM ContextForge](https://github.com/IBM/mcp-context-forge) | MCP/A2A/REST/gRPC 网关、注册、代理、管理 UI、鉴权 | **有上游鉴权/代理，强隔离取决于身份与管理边界** | 更接近工具治理平台，适合多个 MCP 服务。首版工具少时显得重；勿给 AI 上游鉴权透传覆盖能力 |
| [Infisical 主平台](https://github.com/Infisical/infisical) | Secrets、轮换、机器身份、PAM；当前另有 Agent Vault 产品 | **Secrets 获取/环境注入本身不保密；Agent Vault 是另一个代理模式** | 已在用时可作存储后端；否则不必为几个 Key 部署完整系统。SSH PAM 可后续考察 |
| [Vault](https://github.com/hashicorp/vault) | KV、动态凭据、策略；当前另有企业 AI/IAM 功能 | **KV 返回密钥给获准客户端，不等于第三方 HTTP 鉴权代理** | 只让可信 broker 使用 Vault；不把 `kv get` 或读取 token 的 MCP 工具交给 AI。通用调用中心首版不需要它 |
| [Unkey](https://github.com/unkeyed/unkey) | 当前已扩展为 API 开发平台：网关、发放/验证/撤销 Key、权限与限流 | **本次未确认有可直接复用的第三方凭据托管注入模式** | 适合调用中心自身的客户端访问权管理；不要把“管理自家 API Key”误写为“保管所有厂商 Key 并注入”。首版不需要完整平台 |
| [OpenSSH](https://github.com/openssh/openssh-portable) | 成熟 SSH 传输、authorized_keys 限制、forced command | **由可信执行服务持钥；OpenSSH 自己不是 AI 工具中心** | 首版服务器动作首选基础组件；主机别名、参数与远端动作封装仍要写 |
| [Teleport](https://github.com/gravitational/teleport) | 服务器与基础设施访问管理、身份和会话控制 | **基础设施访问边界，与 HTTP API broker 是不同层** | 小规模先不引入；团队服务器多、需要短期身份/会话审计时再评估。源码与官方发行包许可要分别看 |

## 首选的实际注意点

### Agent Vault：最贴题，但不是“装在同用户目录就安全”

官方 [README](https://github.com/Infisical/agent-vault) 确认独立二进制、现成 UI 与默认 SQLite，也明确处于 Preview。最适合复用的是凭据录入、存储、目标服务配置和请求注入，不需要先引入企业平台。

[服务配置](https://docs.agent-vault.dev/learn/services) 支持 Bearer、Basic、API-key 指定 Header、custom 多 Header，另有不注入凭据的 passthrough；也支持在指定位置做占位符替换。替换 URL/body 的范围越宽，越需要限制接口，尤其不能把 refresh token 或 client secret 替换到会回显内容的接口。首版先只用鉴权 Header。

[权限说明](https://docs.agent-vault.dev/learn/permissions) 与 [安全说明](https://docs.agent-vault.dev/learn/security) 显示：vault member/admin 可以通过 CLI 读取/显示凭据，`proxy` 角色不能。应把实例身份限制为 `no-access`，对所需 vault 仅授予 `proxy`，而不是给 AI 管理用户会话。官方安全页有笼统“不返回凭据”的表述，但后面的权限表明确有管理员导出；本项目采用后者这个精确范围。

其 MITM listener 是明文 HTTP forward proxy，代理身份在 agent→broker 链路需要私网/可信网络保护。推荐让可信 MCP 服务在代理机器上使用 loopback/private listener，再对外提供有鉴权的 HTTPS MCP；CA 仅配置到这一服务的 HTTP client。这个组合是本项目提出的架构，**尚未验证与固定 Agent Vault 版本配合的细节**。

已经存在 [Claude Code OAuth 示例](https://docs.agent-vault.dev/guides/oauth-claude-code)，但它不能证明具有各平台通用 OAuth 授权/刷新连接库；要看具体 token 处理路径是否会把 token 返回调用方。

### 连接平台：确有代理，但根访问权仍须封装

[Nango Proxy](https://nango.dev/docs/reference/backend/http-api/proxy/post) 可以加上外部 API 鉴权，但允许基址覆盖，并将上游响应原样返回。连接别名→用户的绑定、固定目标、危险端点筛选应在本项目工具层内完成，调用方不能取得 Nango 的管理/凭据读取能力。

[Composio token custody](https://docs.composio.dev/docs/security/token-custody) 明确区分自己的 API Key 与上游 token：托管执行不要求模型持有上游 token，连接读取默认脱敏。Proxy Execute 对同 scheme/eTLD+1 约束仍允许兄弟子域，权限也比预制工具宽；本项目宜使用固定相对路径和指定工具。托管服务可以持有平台凭据，不能误称“任何软件都无法解密”。

[Pipedream Proxy](https://pipedream.com/docs/connect/api-proxy) 明确支持动态注入鉴权、应用域名白名单和请求限制。它是可用的服务端鉴权模式，不能从 GitHub 上有组件代码推导出后端全部可自部署。

### OpenAPI 自动生成：省重复劳动，不替代选择工具

[FastMCP OpenAPI 文档](https://gofastmcp.com/integrations/openapi) 支持 `from_openapi`，可在 HTTP client 配置鉴权，并用最后一条 catch-all `EXCLUDE` 实现默认拒绝。文档也说明：精心设计的工具通常优于直接镜像全部 REST API。

鉴权参数、基址覆盖、Header、跳转目标、凭据导出操作要在导入过程中筛掉。工具适配器代码、OpenAPI `servers`、远程 `$ref` 与模板都不能让 AI 在运行时自由改写。具体导入流程见 [最小方案](03-最小方案与路线图.md)。

维护上的额外发现：[Unkey README](https://github.com/unkeyed/unkey) 当前暂停外部 PR 接收，但内部提交活跃；这会影响希望长期上游贡献适配器的路线。

## 适合复用什么

| 可复用 | 仍需少量本项目胶水 | 首版暂缓 |
| --- | --- | --- |
| Agent Vault 现成 UI、存储、鉴权 Header 注入 | 中文厂商连接预设、MCP 业务参数与返回值 | 全功能密钥管理平台、多租户计费 |
| FastMCP schema 与 OpenAPI 起步能力 | 激活操作清单、固定 origin、删除鉴权参数 | API 市场、自动抓文档即时上线 |
| 官方云 SDK、OpenSSH | 签名请求可信执行、服务器别名与动作映射 | 任意 shell、完整服务器运维门户 |
| 必要时 Nango/Composio/Pipedream 连接模式 | 限定客户端身份和连接绑定 | 为一个 OAuth 接入先引入完整连接平台 |

候选采用前的固定版本验收在 [路线图](03-最小方案与路线图.md)。没有任何候选被本次研究证明能在“AI 无限 shell + 同权限主机 + 管理会话可控”的环境下单靠隐藏配置实现保密。
