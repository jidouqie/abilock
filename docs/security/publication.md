# 公开内容检查

这是项目长期规则，适用于每次提交、推送、开源、打包和发布，包括仓库、PR、Issue、文档、示例、日志、图片和附件。它只管理公开材料，不检查或拦截用户正常发给业务服务的内容。

## 不公开的内容

- 真实 API Key、密码、私钥、令牌、认证记录、主密钥、凭据库及带凭据 URL。
- 私人服务器或虚拟机的真实地址、账号、用户名、本机路径、机器标识和未授权的个人信息。
- 用户的连接配置、业务提示词与回复、图片、手册导出、日志、截图、安装回执和备份。
- `artifacts/`、运行数据、真实 `.env`、生成的安装包和未审核的二进制文件。

使用 `example.com`、`example.invalid`、`192.0.2.0/24`、`198.51.100.0/24`、`203.0.113.0/24` 及合成账号。临时协议测试可使用回环和明确的合成内网地址。测试秘密优先在运行时生成；固定假值明确标为 mock、fixture 或 example，不复用真实值。

作者主动公开的署名、项目链接、供应商官方域名、公共协议地址和必要系统安装路径可以保留。测试目录不整体豁免；保留的公开 TLS 测试私钥只能按精确路径和固定摘要允许，替换内容必须重新审查。

## 每次发布前

1. 核对拟公开文件和附件，确认没有用户数据。不要为查漏而打开真实凭据库、账户配置或其他项目。
2. 新增文件审查后暂存，运行 `npm run check:public`，同时检查工作树、暂存区和所有分支、标签、远程跟踪及 HEAD 的可达提交历史，包括提交和标签说明。浅克隆不能作为历史已清洁的证据。不读取或发布 Codex 等工具的内部 checkpoint 引用，不使用 `git push --mirror`；它们不属于公开源码。
3. 检查输出只显示类别、路径、行号或提交编号，不把疑似秘密打印到终端、CI 或对话。
4. 提交后再次运行检查，再推送。GitHub 的公开内容工作流会在 push 和 PR 上复查。仓库规则允许时，将该检查设为必需状态。
5. 图片、二进制和未跟踪附件不在文本检查的保证内，逐项人工确认；不要直接上传本机验收目录。

自动检查只覆盖已实现的模式，不能证明不存在所有秘密或个人信息。新增规则和精确例外需要合成测试与人工复核，不能为了让发布通过而扩大豁免。

## 发现问题

立即停止公开或推送。当前文件删除后，旧提交、分支、标签、PR、Actions 日志或附件仍可能保留内容，必须逐项处理。真实凭据已进入可见历史时先由持有人撤销或轮换，再协调历史清理；不要在 Issue 或修复报告里贴出原值。没有明确授权，不重写远程历史或删除用户数据。

本机 `.gitignore` 排除运行状态和验收材料；自动检查不读取这些被忽略的真实数据，也不连接供应商或收费服务。公开测试值可在本机临时回归，系统安装和真实业务调用仍遵守各自的授权流程。
